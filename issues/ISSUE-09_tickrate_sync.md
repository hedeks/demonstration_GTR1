## 1. Проблема и контекст
Ранее компоненты системы GTR1 работали в асинхронном режиме:
1. **PyBullet симулятор** генерировал кадры с плавающей частотой (~30-60 FPS) независимо от скорости обработки C++ пайплайна.
2. **C++ RTR-цикл (`gtr1_main`)** опрашивал кадры через ZMQ SUB, обрабатывал SLGW вокселизацию, запускал нейро-символический планировщик и публиковал телеметрию раздельными топиками (`POSE`, `MAP`, `PATH`).
3. **Web Dashboard (Three.js)** получал раздельные сообщения через WebSocket с сетевым джиттером, что вызывало визуальный лаг между 3D-вокселями карты, позой робота и RGB/Depth кадром в HUD, а также приводило к пропуску или дублированию шагов симуляции при высокой нагрузке.

**Цель:** Реализовать систему детерминированного тикрейта, синхронизирующую состояние карты, позы робота, траектории и кадров симуляции без дрейфа и с нулевым визуальным лагом.

---

## 2. Архитектурное решение

Решение реализовано на двух уровнях:
1. **Lock-Step симуляция (C++ Core <-> PyBullet):**
   - Добавлен режим пошаговой синхронизации `--sync-step` в `src/simulation/pybullet_env.py`.
   - В синхронном режиме симулятор производит ровно один шаг физики (`step_physics_single`), формирует кадр с уникальным инкрементальным `frame_id` (tick) и ожидает подтверждающую команду с соответствующим `frame_id` от C++ ядра перед расчетом следующего кадра.
   - `SimStreamReceiver` в C++ трекает `frame_id` каждого сенсорного пакета и отправляет управляющие команды (`send_command`) с привязкой к текущему `frame_id`.
   - Сохранена полная обратная совместимость со стандартным непрерывным режимом (continuous mode).

2. **Атомарные пакеты телеметрии (`TICK_BUNDLE`):**
   - Вместо разрозненной публикации топиков C++ ядро формирует атомарный JSON-пакет телеметрии:
     ```json
     {
       "type": "TICK_BUNDLE",
       "tick": 142,
       "timestamp_ns": 1697470800000000,
       "pose": { "x": 0.5, "y": 1.2, "z": 0.05, "qx": 0.0, "qy": 0.0, "qz": 0.1, "qw": 0.99 },
       "map": [ { "x": 0.6, "y": 1.0, "z": 0.2, "state": "OCCUPIED" } ],
       "path": [ { "x": 0.0, "y": 0.0 }, { "x": 0.5, "y": 1.2 } ],
       "valences": { ... }
     }
     ```
   - Пакет транслируется через `TelemetryPublisher` (ZMQ PUB 5556) в `ws_bridge.py` и поступает в веб-интерфейс.

3. **Синхронный рендеринг дашборда (Three.js Dashboard):**
   - Добавлен обработчик `handleTickBundle(data)` в `07_infrastructure/dashboard/app.js`.
   - Обновление Three.js мешей позы робота, инстансированного облака вокселей карты (InstancedMesh) и сплайна траектории происходит в рамках одного анимационного кадра `requestAnimationFrame`.
   - В HUD добавлен индикатор синхронизации: `Синхро-тик: #<id>`.

## 5. Оптимизация производительности и GPU-ускорение (Update 2026-10-16)

Для обеспечения строгого 60 FPS рендеринга и исключения лагов при воспроизведении симуляции и датасетов реализованы:
1. **Аппаратное GPU-ускорение CNN1 (NVIDIA CUDA):**
   - В `src/ml_service/cnn1_worker.py` инференс YOLOv8 переведен на `cuda:0` (NVIDIA Quadro P3200).
   - Время инференса одного кадра сокращено до **~40 мс** с минимальной нагрузкой на процессор.
2. **Прореживание карты занятости при строгой синхронности позы:**
   - Поза робота ($SE(3)$), активная цель MTV1, сплайн пути OPRN и номер тика обновляются и транслируются **каждый тик (100% покадровая синхронность)**.
   - Тяжелое облако вокселей карты передается **каждые 5 тиков** (`has_map_update = tick_id % 5 == 0`), что снизило объем JSON-трафика на 80% и полностью устранило блокировку браузерного потока Three.js.

3. **Разделение физики реального времени и контура вычислений (Physics Decoupling):**
   - Физический движок (PyBullet) моделирует физический мир в **реальном астрономическом времени** и не блокируется в ожидании вычислений C++ ядра (робот сказал $v_x = 0.2$ м/с — физика перемещает шасси со скоростью ровно 0.2 м/с в реальном времени).
   - Сенсор камеры снимает раскадровку исходя из **фактического физического положения камеры ($T_{cam}$)** в момент съемки кадра.
   - C++ ядро и Three.js дашборд синхронизируют позу, воксели, распознанные объекты и траекторию строго по `frame_id` этого сенсорного кадра, обеспечивая естественную скорость движения шасси и нулевой лаг отображения.
