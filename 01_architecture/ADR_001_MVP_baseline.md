# ADR 001: Базовые архитектурные решения для MVP (Демонстрации GTR1)

## Контекст
Для реализации первой демонстрации (MVP) информационно-сенсомоторного уровня Гативус (GTR1) необходимо было зафиксировать фундаментальные инженерные рамки: как система будет развертываться, на каких языках программирования писаться, как обмениваться данными и как разрешать базовые конфликты.

## Принятые решения (Архитектурный Контракт)

В ходе технического ревью были приняты следующие 8 критических решений, которые ложатся в основу всей дальнейшей спецификации:

### 1. Топология и Развертывание
* **Решение:** Нативное выполнение на хост-системе (Linux/WSL2) без контейнеризации Docker. Отказ от тяжелого фреймворка ROS 2.
* **Обоснование:** Прямой нативный запуск на хост-системе устраняет накладные расходы виртуализации, проблемы с пробросом GPU (CUDA) и дисплея для GUI/симулятора, а также убирает лишний слой зависимостей от демона Docker. Взаимодействие между модулями осуществляется через легковесный локальный IPC (ZeroMQ), обеспечивающий минимальные субмиллисекундные задержки и отсутствие сетевого оверхеда.

### 2. Технологический стек (Языки)
* **Решение:** Гибридный стек (C++ Core + Python ML).
* **Обоснование:** Язык C++ необходим для обеспечения real-time производительности при работе со структурами MP10-13, расчете SLAM и raycasting'а. Python используется как изолированный сервис для тяжелого инференса ML-моделей (CNN1 - YOLOv8) и среды симуляции PyBullet.

### 3. Среда Симуляции (Ввод/Вывод)
* **Решение:** Двойной режим: физическая 3D-симуляция (PyBullet 60 FPS) и воспроизведение эталонных датасетов (Offline Replay TUM RGB-D). Отказ от ROS 2.
* **Обоснование:** Сочетание нативной симуляции PyBullet и воспроизведения записанных RGB-D датасетов позволяет как отрабатывать замкнутые контуры физического сближения с объектами в реальном времени, так и проводить воспроизводимые регрессионные тесты на фиксированных данных.

### 4. Разрешение коллизий инвариантов (MP11)
* **Решение:** Комбинированное пространственно-семантическое слияние.
* **Обоснование:** Если CNN1 обнаруживает объект, система проверяет дистанцию до существующих объектов в 3D пространстве. Если дистанция мала И совпадает семантический класс (или косинусное сходство эмбеддингов выше порога), новые признаки сливаются с уже существующим UUID.

### 5. Структурное воплощение Валентности
* **Решение:** Поле `valences: List<UUID>` внутри базового абстрактного класса `VALI`.
* **Обоснование:** Открытая валентность (триггер действий) представлена маркером `null` внутри этого массива. Закрытая валентность содержит UUID удовлетворяющего объекта/сплайса. Это классический графовый подход, обеспечивающий максимальную скорость (O(1)) в C++.

### 6. Формат сериализации IPC
* **Решение:** Protocol Buffers (Protobuf).
* **Обоснование:** Строгая типизация и обратная совместимость схем. Protobuf обладает нативной и надежной поддержкой как в C++, так и в Python, что делает его идеальным мостом для передачи структур (например, тензоров MP11) через ZeroMQ.

### 7. Хранилище лога (TRL1)
* **Решение:** Структуры в оперативной памяти C++ (`std::unordered_map`). Отказ от Redis.
* **Обоснование:** Для компактного MVP нет смысла поднимать внешнюю СУБД. Хранение графов завершенных маршрутов в сырой памяти обеспечивает нулевую задержку доступа для предиктора PRD1. При выключении лог может дампиться на диск (например, в тот же Protobuf или JSON).

### 8. Политика Backpressure (Синхронизация потоков)
* **Решение:** Пропуск кадров (Drop Latest / Lossy).
* **Обоснование:** Мы стремимся имитировать строгие real-time ограничения настоящего робота. Если тяжелый оператор (CNN1) не успевает за сенсором (SLAM), промежуточные кадры отбрасываются. Оператор всегда получает самый свежий кадр из "настоящего". Это предотвращает накопление задержки (lag) ценой потери мелкочастотной информации.
